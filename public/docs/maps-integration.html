1. Basics every call shares

Auth. Every /api/maps/* and /api/location/* endpoint requires a Bearer token. There are no anonymous map lookups — the Mapbox key lives on the server and is never shipped to the client.

Authorization: Bearer <accessToken>

Rate limit. /api/maps/* allows 60 lookups per minute per user. Type-ahead is the only thing that gets near it, so debounce autocomplete by ~300 ms. Over the limit you get 429 with { success: false, message: "Too many map lookups…" }.

Envelope. Every response is { success, data } on the way out and { success: false, message } on failure. Read data, not the root.

Coordinate order. Request and response bodies use { lat, lng }. Anything stored on an order as GeoJSON — deliveryLocation.coordinates — is [lng, lat], longitude first. That flip is the single most common integration bug on this API.

2. The address picker

Four endpoints, used in this order.

EndpointQueryReturns
GET/api/maps/places/autocomplete input, sessiontoken Suggestions as the user types (Nigeria only)
GET/api/maps/places/details placeId, sessiontoken Coordinates + formatted address for one suggestion
GET/api/maps/geocode address Coordinates for a typed-out address
GET/api/maps/reverse-geocode lat, lng Address for a dropped pin / GPS fix

Session tokens

Generate one UUID when the picker opens, send it with every autocomplete keystroke and the final details call, then throw it away. One token per address chosen. Reusing a token across addresses, or omitting it, is billed as separate lookups.

class AddressPicker {
  final _dio = Dio();
  String _session = const Uuid().v4();   // one per address chosen

  Future<List<dynamic>> suggest(String input) async {
    if (input.trim().length < 3) return [];
    final r = await _dio.get('/api/maps/places/autocomplete',
        queryParameters: {'input': input, 'sessiontoken': _session});
    return r.data['data']['predictions'] as List;
  }

  Future<Map<String, dynamic>> choose(String placeId) async {
    final r = await _dio.get('/api/maps/places/details',
        queryParameters: {'placeId': placeId, 'sessiontoken': _session});
    _session = const Uuid().v4();        // token is spent — start a new one
    return r.data['data'];               // { lat, lng, formattedAddress, ... }
  }
}

3. Delivery fee preview

Distance and drive time between two points:

GET /api/maps/distance
    ?originLat=6.5244&originLng=3.3792
    &destLat=6.4281&destLng=3.4219

The fee the backend will charge follows this tariff:

RuleValue
Base fee (covers the first 5 km)₦1,200
Every kilometre beyond 5 km₦100
Maximum delivery distance100 km

So a 12 km delivery is ₦1,200 + (7 × ₦100) = ₦1,900. Mirror that arithmetic in the client for a preview, but treat the figure on the created order as the truth — see the gotcha below.

4. Placing the order

POST/api/order/create — send deliveryLocation alongside the usual fields:

{
  "deliveryAddress": "12 Adeola Odeku St, Victoria Island, Lagos",
  "deliveryLocation": {
    "lat": 6.4281,
    "lng": 3.4219,
    "formattedAddress": "12 Adeola Odeku St, Victoria Island, Lagos"
  }
}

Send lat/lng — that is the path the server uses to compute a real distance-based fee. Without coordinates the order still succeeds, but the fee falls back to the flat base fee.

6. Live tracking over WebSocket

Endpoint: wss://<host>/ws/location?token=<accessToken>. The token may also travel as an Authorization: Bearer header; the query parameter exists because most Flutter WebSocket clients cannot set headers.

Messages you send

MessageWhen
{"type":"subscribe_order","orderId":"…"}After the tracking screen opens
{"type":"unsubscribe_order","orderId":"…"}When it closes
{"type":"ping"}Every ~30 s to hold the connection open

Messages you receive

TypePayload
connectionmessage, userId, timestamp — the handshake succeeded
subscribed / unsubscribedorderId, message
location_updatedeliveryAgentId, orderId, timestamp, and location — see the table below
pongtimestamp
errormessage — malformed or unknown message type
 
final ws = WebSocketChannel.connect(
  Uri.parse('wss://$host/ws/location?token=$accessToken'),
);

ws.sink.add(jsonEncode({'type': 'subscribe_order', 'orderId': orderId}));

ws.stream.listen((raw) {
  final msg = jsonDecode(raw);
  if (msg['type'] != 'location_update') return;

  final loc = msg['location'];            // keys are latitude / longitude
  controller.moveRider(LatLng(loc['latitude'], loc['longitude']));

  // Null means "no fresh value this ping" — keep showing the last ETA.
  if (loc['etaSeconds'] != null) controller.setEta(loc['etaText']);

  // The rider left the route and the server planned a new one.
  if (loc['rerouted'] == true && loc['route'] != null) {
    controller.replaceRoute(decodePolyline(loc['route']['polyline']));
  }
});

// keep-alive
Timer.periodic(const Duration(seconds: 30),
    (_) => ws.sink.add(jsonEncode({'type': 'ping'})));

The location payload

FieldTypeMeaning
latitude, longitudenumberRider position. Not lat/lng, and not GeoJSON.
addressstringStreet address of the rider's position
etaSecondsnumber / nullSeconds until the order reaches the buyer
etaTextstring / nullThe same ETA, formatted, e.g. "18 mins"
nextStop"pickup" / "dropoff" / nullWhere the rider is heading now
reroutedbooleanTrue when the server just planned a new route
routeobject, only when reroutedpolyline (polyline5), distance (m), duration (s), steps, estimatedArrival
status, timestampstringTracking state and time of the ping

ETA and rerouting

The server recalculates both on every rider ping, so the client only draws what arrives.

  • ETA is always to the buyer's door. While nextStop is "pickup" it includes the trip to the store and then on to the buyer. After the rider marks the order picked up, it is measured straight to the buyer.
  • etaSeconds can be null when the order has no delivery coordinates (the buyer typed an address that was never matched to a map location), when the store has no map location and pickup is still pending, or when the maps lookup failed on that ping. Keep the last value you showed rather than blanking it.
  • Rerouting happens when the rider is more than 50 m from the route line, plus the phone's reported GPS accuracy (up to 50 m more). When rerouted is true, replace the drawn line with route.polyline. Other pings leave the current line in place.
A closed socket is normal on mobile — backgrounding kills it. Reconnect with backoff and re-send subscribe_order: subscriptions live per socket and are not restored for you. While disconnected, fall back to GET /api/location/current/:orderId.

REST fallbacks

EndpointUse
GET/api/location/current/:orderIdLast known rider position — poll ~15 s while the socket is down
GET/api/location/history/:orderIdThe breadcrumb trail already travelled

7. The dispatch rider's side

These require the dispatch role and are for the rider app, not the buyer app.

EndpointUse
GET/api/delivery-agent/orders/activeThe rider's current order, with pickup and dropoff as { address, lat, lng, mobile }. Open the tracking screen with this.
POST/api/location/routeFirst route for the order from the rider's position: through the store until pickup, then straight to the buyer
POST/api/location/updatePush the rider's position. The response carries the same eta, nextStop, rerouted and route as the socket, so the rider app doesn't need to subscribe.
PUT/api/delivery-agent/orders/statusMove the order forward: picked_up, in_transit, failed. Sending picked_up is what changes nextStop to "dropoff".
PUT/api/location/statusOptional map display state only (en_route, arrived). Does not change the order.
POST/api/delivery-agent/orders/confirm-deliveryRider's half of completing the delivery. The buyer confirms too (POST /api/order/confirm-delivery); the rider is paid once both have confirmed.

The route polyline is polyline5 encoded — decode it before handing it to the map (flutter_polyline_points or equivalent).

Ping about every 10 seconds while the rider is moving, and skip pings while they are standing still. Each ping makes paid maps calls on the server, so don't ping more often than every 5 seconds.

No endpoint accepts delivered as a status. Deliveries finish only through the two confirm calls above.

8. Gotchas

SymptomCause
Marker lands in the sea off Ghana[lng, lat] read as [lat, lng]. Null Island is 0,0.
Fee is exactly ₦1,200 regardless of distanceNo coordinates on the order, or the upstream lookup failed. The tariff silently falls back to the flat base fee — it never errors. Always show the fee from the created order, not your own estimate.
429 from autocompleteUndebounced type-ahead. Debounce ~300 ms and require 3+ characters.
No location_update ever arrivesNo rider assigned yet (deliveryAgent is null), or the socket reconnected without re-subscribing.
Autocomplete billed twice per addressA fresh session token per keystroke. One token per address, spent on the details call.
Rider marker never movesReading location['lat']. The keys are latitude and longitude.
ETA shows the store trip after pickupThe rider app never sent picked_up to PUT /api/delivery-agent/orders/status, so nextStop is still "pickup".
ETA is always nullThe order has no delivery coordinates. Send lat/lng when creating the order.
Route line ignores the rider's detourThe client isn't replacing the line when rerouted is true.
Socket dies after a few minutes idleNo keep-alive. Send ping every 30 s.

Checklist

  • Bearer token on every maps and tracking call
  • Autocomplete debounced, 3-character minimum, one session token per address
  • lat/lng sent on POST /api/order/create
  • GeoJSON read as [lng, lat]
  • Delivery fee displayed from the order, not from a client-side estimate
  • WebSocket: subscribe on open, re-subscribe on reconnect, ping every 30 s, unsubscribe on close
  • REST polling fallback while the socket is down
  • Rider position read from latitude/longitude
  • Last ETA kept when etaSeconds is null; route line replaced when rerouted is true
  • Rider app sends picked_up to the order-status endpoint, and pings about every 10 s while moving
